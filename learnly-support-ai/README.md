# Learnly Support AI

AI-агент підтримки онлайн-школи, який **не лише відповідає, а розв'язує проблему**: перевіряє реальний стан системи, з'ясовує справжню причину звернення, ставить уточнювальні питання, виконує дозволені дії, а все, що йому робити заборонено, передає адміністратору з готовим рішенням. Кожну перевірку й дію записує в аудит.

PolyTech Code Fest · трек «AI Customer Support Automation» · Team17

## Швидкий старт

```bash
pip install -r requirements.txt
cp .env.example .env                          # ключ Gemini — опційно, див. нижче
python -m uvicorn app.main:app --port 8000    # → http://localhost:8000
pytest -q                                     # 95 тестів
```

- Python 3.11+. Окрема база не потрібна: SQLite-файл `data/learnly.db` створюється сам і наповнюється демо-даними.
- Щоб почати з нуля, натисніть у шапці **«Скинути стан»** або видаліть `data/learnly.db`.
- Сторінка відкривається в кабінеті викладача. Інші кабінети — через **«Змінити роль / Вийти»**.

### Як увімкнути AI (Gemini)

1. Візьміть безкоштовний ключ на <https://aistudio.google.com/apikey>.
2. Впишіть у `.env`: `GEMINI_API_KEY=<ключ>`. Модель за замовчуванням — `LLM_MODEL=gemini-3.5-flash-lite` (швидка, ~1–4 с на відповідь).
3. Перезапустіть сервер. `GET /api/health` поверне `"llm": true`, а в картці аналізу копілота з'явиться «(Gemini)» замість «(правила)».

Без ключа, а також коли LLM недоступний, перевищено квоту чи відповідь невалідна, система **автоматично** переходить на детерміновані правила. Демо працює завжди, навіть без інтернету.

## Що вміє (за ролями)

| Роль | Сценарій | Що робить агент |
|---|---|---|
| **Батьки** ⭐ | Оплата пройшла, але заняття не з'явились: платіж оформлено на пошту з одруківкою (за досвідом ментора — ~40% звернень) | Через MCP перевіряє акаунт → людина не знає про одруківку, тож агент **сам шукає** неприв'язані оплати на цю суму зі схожою поштою й знаходить платіж на `gmial.com` → **перевіряє власника** (останні 4 цифри картки, деталі до підтвердження не розкриває) і **пам'ятає контекст** → прив'язати сам не може (MCP забороняє агенту фінансовий запис) → створює тікет P1 із трасуванням перевірок і **готовим рішенням** |
| **Адміністратор** | Черга ескалацій | Бачить, що саме перевірив агент (кожен виклик MCP з аргументами й результатом), бере тікет у роботу, **виконує рішення агента одним кліком**. Результат автоматично повертається в чат користувача, баланс оновлюється |
| **Адміністратор → AI-копілот** | Звернення учнів курсів | Визначає **справжню мету** («хочу повернути гроші» → насправді бракує часу), тон (зокрема сарказм) і ризик відтоку. Пропонує дії з перевіркою політики, які людина підтверджує, і пише чернетку відповіді з оцінкою якості |
| **Адміністратор → Ефективність** | Дашборд | Виконані й заблоковані дії AI, врятовані від повернення учні (грн), якість AI-чернеток проти ручних відповідей, зекономлений час, звернення за наміром |
| **Викладач** | Подвійне бронювання слота | Аналізує календар і час бронювань, пропонує вільні слоти. **Без підтвердження викладача нічого не змінює** |
| **Викладач** | Учень у календарі після завершення курсу | Ескалює адміністратору; після рішення слот звільняється в календарі |
| **Учень** | Не приходить SMS-код / не відображається ДЗ | Пояснює причину й пропонує вихід (див. обмеження) |

В усіх чатах агент доречно реагує на привітання, жарти й сарказм. Він не запускає випадковий сценарій і не створює зайвих тікетів.

### Демо за 2 хвилини

1. **Скинути стан** → роль **Батьки** → кнопка «💸 Оплата 2,400 грн пройшла…» → агент через MCP сам знаходить оплату на пошту з одруківкою (`oks***@gmial.com`) і просить підтвердити картку.
2. Відповісти `4417` → власника підтверджено, MCP відмовляє агенту у фінансовому записі (⛔), створюється тікет P1 з готовим рішенням.
3. Роль **Адміністратор** → тікет Оксани → перевірки агента й готове рішення → **«Виконати рішення агента»**.
4. Знову **Батьки** → у чаті оновлення від агента, баланс змінився з 0 на 8 занять.
5. **Адміністратор → 🤖 AI-копілот** → «Олена Коваль» → «Надіслати звернення» → справжня мета «бракує часу» → підтвердити перенос → **📊 Ефективність**: +1 врятований учень.

## Архітектура

```
Браузер — static/index.html (один файл, vanilla JS, без збірки)
   │ REST/JSON
FastAPI — app/main.py
   │   middleware: змінюючі запити виконуються по черзі; після кожного стан зберігається в SQLite
   │
   ├── Агенти (розуміння й рішення)
   │     app/agent.py          копілот: намір → справжня мета → дії → чернетка; тон/сарказм; чат ролей
   │     app/teacher_agent.py  календар викладача: конфлікти бронювань, застарілі записи
   │     LLM: Gemini ──(немає ключа / збій / невалідний JSON)──► правила
   │
   ├── MCP-шлюз — app/mcp.py: ЄДИНИЙ шлях агента до даних школи
   │     білий список інструментів · агент читає, записує лише адмін · приховані поля
   │     пошук лише з фільтром, ≤5 рядків · кожен виклик → audit log
   │
   ├── Policy-guard — app/tools.py + app/policy.py: дії копілота
   │     check() перевіряє правила школи незалежно від того, що «сказав» LLM;
   │     ризик low/medium/high → medium/high потребують підтвердження людиною
   │
   └── Стан і аудит — app/store.py + app/db.py (SQLite)
         учні, тікети, ескалації з історією, пам'ять чатів, audit log
```

### Принципи безпеки

1. **LLM ніколи не змінює дані сам.** Він лише пропонує дію, а виконує її код після перевірки політики (`tools.check`) або MCP-шлюзу.
2. **Мінімальний доступ.** Агент бачить дані школи лише через `app/mcp.py`. Пароль, телефон і повний номер картки за межі шлюзу не виходять. Вивантажити таблицю неможливо.
3. **Фінанси — тільки людина.** `link_payment` дозволено лише ролі `admin`. Агент готує рішення, адміністратор його виконує.
4. **Прозорість.** Кожен виклик MCP, дія, ескалація й рішення пишуться в audit log. В історії тікета видно, хто, що й коли зробив.
5. **Відмовостійкість.** Збій LLM не ламає підтримку: працює запасний режим на правилах.

### Де працює LLM, а де правила, і чому

| Шар | Як працює |
|---|---|
| Аналіз звернення в копілоті (намір, справжня мета, тон, дії, чернетка) | **Gemini** (JSON-схема) → валідація → policy-guard; запасний варіант — правила |
| Відповіді в чатах поза відомими сценаріями (привітання, жарт, незрозумілий запит) | **Gemini** з історією розмови; запасний варіант — шаблони |
| Відомі, перевірені сценарії (оплата, бронювання) | Детермінована логіка + MCP |
| Пріоритет, ризик відтоку, оцінка якості відповіді | Код (відтворювано й пояснювано) |

Це свідомий вибір проти двох головних проблем AI-підтримки — **довіри й вартості**. Повторювані перевірені рішення виконуються правилами (безкоштовно й передбачувано), а LLM підключається там, де потрібне розуміння мови.

## Структура

```
app/
  main.py           REST API, сценарії ролей, ескалації, адмінка
  agent.py          копілот + чат ролей: LLM-шлях і запасні правила, тон/сарказм
  teacher_agent.py  агент календаря викладача
  mcp.py            MCP-шлюз: білий список, доступ за роллю, приховані поля, аудит
  tools.py          дії копілота з policy-guard (check + run)
  policy.py         правила школи (вікно повернення 14 днів, ліміти тощо)
  context.py        похідний контекст учня (дні з оплати, темп, дублі платежів)
  quality.py        оцінка якості відповідей агентів
  store.py, db.py   стан + SQLite
  data.py           демо-дані
static/index.html   інтерфейс (4 кабінети)
tests/              95 тестів pytest
docs/features/ai-support-copilot/   документація фічі
```

### Основні ендпоінти

| Метод | Шлях | Призначення |
|---|---|---|
| POST | `/api/role-chat` | Чат учня/викладача/батьків (з пам'яттю розмови) |
| POST | `/api/role-chat/updates?role=` | Рішення адміністратора, які ще не доставлено в чат |
| GET | `/api/admin/escalations?status=&priority=` | Черга ескалацій |
| POST | `/api/admin/escalations/{id}/take` · `/resolve` | Взяти в роботу / вирішити (виконує готове рішення агента через MCP) |
| GET | `/api/mcp/tools` | Каталог MCP: інструменти, доступ, поля, приховані поля |
| POST | `/api/tickets` · `/api/tickets/{id}/actions/{aid}/approve` | Копілот: звернення учня / підтвердження дії |
| GET | `/api/analytics` · `/api/audit` | Ефективність підтримки / журнал аудиту |
| POST | `/api/teacher-chat` · `/resolve-booking` | Агент календаря викладача |

### Тести

`pytest -q` — 95 тестів без мережі (окрема база в пам'яті, без LLM). Що покрито:
- бізнес-кейси розуміння звернень, серед них «справжня мета», сарказм і жарти;
- policy-guard;
- MCP-шлюз: заборона запису агенту, пошуку без фільтра, інструментів поза білим списком, приховані поля;
- сценарій оплати з уточненням і пам'яттю;
- життєвий цикл тікета й доставка рішення в чат;
- збереження стану після перезапуску;
- агент викладача.

## Обмеження MVP (чесно)

- **MCP** — шлюз із контрактом MCP усередині процесу застосунку. У продакшні той самий контракт виноситься в окремий MCP-сервер.
- **Сценарії учня і «друга дитина»** повертають підготовлені відповіді. Повністю реалізовані батьки (оплата), викладач і адміністратор.
- **Дані — демо.** Дати рахуються відносно першого запуску, тож перед показом варто «Скинути стан». Авторизації немає: ролі перемикаються вручну.
- **Roadmap:** окремий MCP-сервер, Postgres і міграції, авторизація, перетворення перевірених LLM-рішень на правила (кеш рішень), інтеграції з Zendesk/Intercom.
