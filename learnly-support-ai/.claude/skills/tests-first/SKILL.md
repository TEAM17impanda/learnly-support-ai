# Тести перед кодом

Зелені тести ≠ правильна фіча, якщо тести підігнані під реалізацію. Тому:

1. **Опиши бізнес-кейс одним реченням** (хто, що написав, що має статися).
2. **Запиши очікуваний результат з бізнес-правил**, а не з того, що вже видає код:
   ```
   Учень оплатив 20 днів тому, просить повернення → вікно 14 днів закрите →
   AI НЕ пропонує request_refund, пропонує пояснення політики + escalate_to_human
   ```
3. **Напиши тест, який падає** (`pytest -q` → red).
4. Тільки тоді реалізуй. Не змінюй тест, щоб він позеленів — якщо тест здається хибним, зупинись і переглянь правило.
5. Для кожного кейсу — три категорії: щасливий шлях, порушення політики, шумні/неочікувані дані (порожнє повідомлення, невідомий учень, повторне підтвердження).

## Мінімальний набір для цього проєкту
- `tests/test_agent.py` — інтент, справжня мета, рекомендована дія, **fallback без LLM**
- `tests/test_tools.py` — кожен tool: OK + порушення політики
- `tests/test_api.py` — наскрізний флоу: звернення → аналіз → approve → зміна стану → аналітика
- Якість відповідей: `tests/test_quality.py` (добра vs груба відповідь)

## Команда
```bash
pytest -q          # має бути зелено перед кожним комітом
```

## Антипатерни
- Тест перевіряє, що функція «повертає те, що повертає»
- Мок LLM, який повертає саме ту відповідь, яку очікує тест (тестуй fallback-правила й валідацію, а не мок)
- Видалення падаючого тесту
